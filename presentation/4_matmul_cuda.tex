\section{Optimizing \textbf{Ge}neral \textbf{M}atrix \textbf{M}ultiplication (GEMM) on CUDA}

\begin{frame}[fragile]
  \frametitle{What is GEMM?}
  \begin{block}{Definition: Single-precision general matrix multiplication (SGEMM)}
    \[
      C \leftarrow \alpha AB + \beta C
    \]
  \end{block}

  \begin{itemize}
    \item Setting $\alpha=1$ and $\beta=0$ gives ordinary matrix multiplication: $C=AB$.
    \item Other values let one call scale the product and accumulate it into an existing matrix.
  \end{itemize}

  \begin{onlyenv}<1>
    \begin{example}
      During the forward pass when training a model, we accumulate the gradients
      from the entire batch.
    \end{example}
  \end{onlyenv}

  \begin{onlyenv}<2>
    \begin{columns}
      \begin{column}{.5\linewidth}
        \begin{lstlisting}
sgemm(
  int M, int N, int K,
  float alpha, float *A, float *B,
  float beta, float *C
)
        \end{lstlisting}
      \end{column}

      \begin{column}{.5\linewidth}
        \[
          \underbrace{A}_{M\times K} \quad
          \underbrace{B}_{K\times N} \quad
          \underbrace{C}_{M\times N}
        \]

        \begin{itemize}
          \item \(M\): rows of \(A\) and \(C\)
          \item \(N\): columns of \(B\) and \(C\)
          \item \(K\): shared reduction dimension
        \end{itemize}
      \end{column}
    \end{columns}
  \end{onlyenv}

\end{frame}

\begin{frame}
  \frametitle{Naive SGEMM Kernel (idea)}
  Let's design a SGEMM kernel!
  \pause
  \begin{block}{Recall}
    Recall that matrix multiplication is naturally parallel, and the output
    elements of \(C\) can be computed independently in parallel.
    \includegraphics[width=\linewidth]{matmul.png}
  \end{block}
  \pause
  \textbf{We can naturally map one thread to each output element!}

\begin{frame}[fragile]
  \frametitle{Naive SGEMM Kernel}

  \begin{columns}
    \begin{column}{0.6\linewidth}
      \begin{lstlisting}[
    basicstyle=\ttfamily\fontsize{6}{6.8}\selectfont
  ]
__global__ void sgemm_naive(
    int M, int N, int K, float alpha, const float *A,
    const float *B, float beta, float *C
) {
  const uint x = blockIdx.x * blockDim.x + threadIdx.x;
  const uint y = blockIdx.y * blockDim.y + threadIdx.y;

  if (x < M && y < N) {
    float tmp = 0.0;
    for (int i = 0; i < K; ++i)
      tmp += A[x*K+i] * B[i*N+y];
    C[x*N+y] = alpha*tmp + beta*C[x*N+y];
  }
}
void run_sgemm_naive(
  int M, int N, int K, float alpha, float *A,
  float *B, float beta, float *C
) {
  dim3 blockDim(32, 32);
  dim3 gridDim(CEIL_DIV(M, 32), CEIL_DIV(N, 32));
  sgemm_naive<<<gridDim, blockDim>>>(
      M, N, K, alpha, A, B, beta, C);
}

\begin{frame}
  \frametitle{We can do better}
  \textbf{Observed latency: 3.55s}.

  \pause
  A SGEMM with $m,n,k = 8192$ requires \(~2(8192)^3 = 1.10\times10^{12} \) FLOPs.

  \pause
  These benchmarks were run on an RTX 3090 with \textbf{35.6 TFLOP/s}
  of peak FP32 \textbf{throughput}.

  \pause
  Therefore, if we achieve peak FP32 throughput, we should have a latency of
  \[ \frac{1.10\ \text{TFLOP}}{35.6\ \text{TFLOP/s}} \approx 0.031 \text{s} = 31\text{ms}.\]

  \pause
  \begin{alertblock}{Whats the hold up?}
    Our observed latency of 3.55 \emph{seconds} is more than \(100\times\) the
    theoretical minimum of 31 \emph{milliseconds}!
  \end{alertblock}
\end{frame}

\begin{frame}
  \frametitle{We aren't considering memory bandwidth.}
  Every thread is \textbf{reading everything from DRAM} for each element it needs. \pause

  We assigned a thread to each output element, so we have \(m \times n \times (2k) = 2(8192)^3\)
  DRAM accesses for the matmul portion. At FP32, that is
  \(2(8192)^3 \times 4 \text{ bytes} \approx 3298.5 \text{ GB}\). \pause

  The RTX 3090 has a DRAM bandwidth of \(935.8\) GB/s. So the time required
  to serve all the DRAM requests is \(3298.5 / 935.8 \approx 3.52\)s. \pause

  \begin{alertblock}{We are memory bound!}
    Our observed latency of 3.55 seconds is dominated by the time it takes to
    move the data from DRAM to the CUDA Cores, so we are \textbf{memory bound}.
    Our CUDA Cores are sitting idle for most of the time!
  \end{alertblock}
\end{frame}

\begin{frame}
  \frametitle{Shared Memory (SMEM) Caching}
  \begin{block}{Programmable L1 Cache (SMEM)}
    Remember how our launch config. required us to group threads as blocks?
    That is because \textbf{blocks} are scheduled to SM's as a unit, so threads
    in the same block have access to the SM's L1 cache/SMEM.
  \end{block}

  \centering
  \includegraphics[width=0.90\linewidth]{cuda-programming-model.png}

  {\tiny Image source: \href{https://modal.com/gpu-glossary/device-software/cuda-programming-model}{Modal, ``CUDA Programming Model,'' \emph{GPU Glossary}.}}
\end{frame}

\begin{frame}
  \frametitle{Tiling}
  Threads can save time by loading data from Device/Global memory into Shared Memory within the SM.
  \begin{block}{Main Idea}
    Before doing any computation, load a chunk of the necessary data from DRAM
    to SMEM as a block. Then, memory accesses for the computation now only go to SMEM.
  \end{block}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Basic tiled SGEMM}

  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.75\textwidth}
      \begin{lstlisting}[
        basicstyle=\ttfamily\fontsize{7}{7.8}\selectfont,
        escapeinside={(*@}{@*)}
      ]
__shared__ float As[BLOCKSIZE * BLOCKSIZE];
__shared__ float Bs[BLOCKSIZE * BLOCKSIZE];
float tmp = 0.0;

for (int bkIdx = 0; bkIdx < K; bkIdx += BLOCKSIZE) {
  As[threadRow * BLOCKSIZE + threadCol] =
      A[threadRow * K + threadCol];
  Bs[threadRow * BLOCKSIZE + threadCol] =
      B[threadRow * N + threadCol]; (*@\tikz[remember picture,overlay]\coordinate (tile-load);@*)

  __syncthreads(); (*@\tikz[remember picture,overlay]\coordinate (tile-ready);@*)
  A += BLOCKSIZE;
  B += BLOCKSIZE * N;

  for (int dotIdx = 0; dotIdx < BLOCKSIZE; ++dotIdx) {
    tmp += As[threadRow * BLOCKSIZE + dotIdx] *
           Bs[dotIdx * BLOCKSIZE + threadCol]; (*@\tikz[remember picture,overlay]\coordinate (tile-compute);@*)
  }

  __syncthreads(); (*@\tikz[remember picture,overlay]\coordinate (tile-next);@*)
}
      \end{lstlisting}
    \end{column}

    \begin{column}{0.25\textwidth}
      \begin{tikzpicture}[remember picture,
          callout/.style={draw,rounded corners,fill=#1!10,
          text width=0.92\linewidth,inner sep=3pt,font=\scriptsize}
        ]
        \node[callout=codecuda] (load-note) {\textbf{Cooperate}\par
        Each thread loads one value from $A$ and one from $B$.};
        \node[callout=blue,below=4mm of load-note] (ready-note) {\textbf{Synchronize}\par
        Wait until both shared tiles are complete.};
        \node[callout=orange,below=4mm of ready-note] (compute-note) {\textbf{Reuse}\par
        One thread accumulates from the cached row and column.};
        \node[callout=codecomment,below=4mm of compute-note] (next-note) {\textbf{Advance}\par
        Protect the cache, move along $K$, and repeat.};
      \end{tikzpicture}
    \end{column}
  \end{columns}

\begin{frame}
  \frametitle{Can we still do better?}

  \begin{block}{Throughput analysis}
    We report a final latency of \(0.36\)s or \(360\)ms for \(n=8192\).
    This is around \(10\times\) the theoretical minimum of $31$ms. This slowdown
    suggests we are still \textbf{memory bound}.
  \end{block}

  \pause
  This tiling setup with \(32 \times 32\) blocks and \(n, m, k = 8192\), we need
  a \textbf{grid} of \(\frac{m}{32} \times \frac{n}{32} = 256\times 256 = 65,536\) blocks.

  \pause
  Each block loads \(\frac{k}{32} = 256\) tiles from both \(A\) and \(B\).
  \pause Each tile is \(32\times 32\) elements.

  \pause
  Thus, we have
  \[
    \underbrace{65,536}_{\text{blocks}}
    \times \underbrace{256}_{\text{tiles/block}}
    \times \underbrace{2}_{A\text{ and }B}
    \times \underbrace{32 \times 32}_{\text{elements/tile}}
    \times \underbrace{4\text{ bytes}}_{\text{bytes/element}}
    \approx 137.7\text{ GB}.
  \]

  \pause
  At \(935.8 \text{ GB/s}\), we need 0.147s or 147ms to move all data from DRAM
  to SMEM.
\end{frame}

\begin{frame}
  \frametitle{This type of analysis is getting hard...}
  When we did this analysis for the \textbf{naive kernel}, it was easy to see how
  the data moved, and at the end of it, we even got the nice result of
  \[
    \underbrace{3.55\text{s}}_{\text{Observed latency}}
    \approx \underbrace{3.52\text{s}}_{\text{Time to move data}}
    + \underbrace{0.031\text{s}}_{\text{Theoretical minimum for work}}.
  \]

  \pause However, as we apply more optimizations, \textbf{predicting performance
  based on hardware specifications becomes impractical.} \pause Even with just
  our \textbf{basic tiling kernel}, the observed latency of
  \[
    \underbrace{360\text{ms}}_{\text{Observed latency}}
    \ne \underbrace{147\text{ms}}_{\text{Time to move data}}
    + \underbrace{32\text{ms}}_{\text{Theoretical minimum for work}}
    = 179\text{ms}.
  \]

  \pause This gap comes from things like occupancy, synchronization overhead, bank conflicts...
  \pause \textbf{Without profiling every possible source of latency, can we still
  determine whether memory is the bottleneck}?
\end{frame}

\begin{frame}
  \frametitle{Throughput as a performance measure}
  So far, we have been measuring and comparing \textbf{latency}. However, a better
  measure of performance is \textbf{throughput}. \pause
  \begin{block}{Throughput}
    Formally stated, \textbf{throughput} is the total useful work (FLOPs) done
    per unit time. \emph{We previously discussed theoretical peak throughput}.
    \[
      \mathrm{Throughput} = \frac{\mathrm{FLOPs}}{\mathrm{time}}
    \]
  \end{block}

  \pause
  Kernels are used with varying task sizes. Reporting latency doesn't tell you
  anything about how the kernel actually behaves as we scale!
\end{frame}

\begin{frame}
  \frametitle{Arithmetic intensity and the Roofline Model}

  \only<1>{
    \begin{example}
      Theoretical peak throughput of our 3090 is $35.6$ TFLOP/s. We observed $360$ms or $0.36$s
      of latency for \(n=8192\), where the total FLOPs required is \(1.10\) TFLOPs.

      Thus, we have an observed throughput of
      \[\frac{1.10\mathrm{ TFLOPs}}{0.36\mathrm{s}} \approx 3.05\mathrm{TFLOP/s}. \]

      Roughly $10$\% of peak throughput.
    \end{example}

  }

  \only<2>{

    \begin{block}{Arithmetic Intensity}
      We define the \textbf{Arithmetic Intensity} (AI) of our kernel as the
      number of FLOPs done per bytes moved from DRAM.
      \[
        \mathrm{AI}=\frac{\mathrm{FLOPs}}{\mathrm{bytes\ moved}}
      \]
    \end{block}

    \begin{example}
      For \(n=8192\) and $32\times32$ tiles, the grid contains
      $256^2=65{,}536$ blocks. Each block takes 256 steps, loading one tile
      from both $A$ and $B$ per step, then writes one tile to $C$.
      \[
        \begin{aligned}
          \mathrm{bytes/block}
          &= \left(256\times2\times32^2+32^2\right)\times4
          = 2{,}101{,}248\ \mathrm{bytes}, \\
          \mathrm{bytes\ total}
          &= 65{,}536\times2{,}101{,}248
          \approx \boxed{137.7\ \mathrm{GB}}.
        \end{aligned}
      \]
    \end{example}
  }

  \only<3>{
    \begin{example}[cont.]
      For \(n=8192\) and $32\times32$ tiles, the grid contains
      $256^2=65{,}536$ blocks. Each block takes 256 steps, loading one tile
      from both $A$ and $B$ per step, then writes one tile to $C$.
      Across the complete grid, the kernel moves
      \[
        65{,}536\left(256\times2\times32^2+32^2\right)\times4
        \approx 137.7\ \mathrm{GB}.
      \]

      With a total work count of $1.10$ TFLOP, its arithmetic intensity is
      \[
        \mathrm{AI}
        = \frac{1.10\times10^{12}\ \mathrm{FLOP}}
        {137.7\times10^9\ \mathrm{bytes}}
        \approx \boxed{8.0\ \mathrm{FLOP/byte}}.
      \]
    \end{example}
  }

  \only<4>{
    \begin{block}{Roofline Model}
      For a given system, we can predict a the upper bound of throughput of a
      kernel given its AI. Up to a certain point, increasing AI will raise the
      upper bound of throughput. However, at the \textbf{ridge point}, we become
      \textbf{compute bound}, and no longer benefit from increasing AI.
    \end{block}
    \begin{example}
      For our 3090, we have $35.6$ TFLOP/s of peak FP32 throughput and $936$ GB/s
      of memory bandwidth. Thus, our ridge point is

      \[ \mathrm{RP} = \frac{35.6 \times 10^{12} \mathrm{FLOP/s}}{936 \times 10^9 \mathrm{bytes/s}} \approx 38.0 \mathrm{FLOPs/byte}\]

    \end{example}
  }

    \centering
    \includegraphics[width=0.9\textwidth]{generated/rtx3090_roofline.png}
  }
\end{frame}

\begin{frame}
  \frametitle{Thread coarsening: Increasing AI}
  \begin{itemize}
    \item Basic tiling assigns $1$ element of the output to each thread.
    \item We can \emph{coarsen} each thread, and assign a $TM \times TN$ portion of the output to each thread.
    \item We load larger chunks into SMEM, increasing data reuse and AI.
    \item One loaded $A$ value can update several columns; one loaded $B$ value can update several rows.
  \end{itemize}

\end{frame}

\begin{frame}
  \frametitle{We have only scratched the surface: cuBLAS}
  \begin{itemize}
    \item cuBLAS is NVIDIA's architecture-tuned linear algebra library and the
      practical performance target for our SGEMM kernels.
    \item At $n=8192$, cuBLAS reaches $27.38$ TFLOP/s, while our fastest
      configuration (C4) reaches $19.54$ TFLOP/s, or $71.4\%$ of cuBLAS's
      throughput.
    \item cuBLAS completes the multiplication in $40.2$ ms versus $56.3$ ms
      for C4, about $1.40\times$ faster.
  \end{itemize}
  \begin{block}{The remaining gap}
    Production kernels combine deeper register and warp tiling, vectorized
    memory access, pipelined loads, and architecture-specific instruction
    scheduling.
  \end{block}
\end{frame}
